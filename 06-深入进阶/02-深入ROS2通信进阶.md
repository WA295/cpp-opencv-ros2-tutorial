## 1. QoS 不匹配：最隐蔽的坑

### 1.1 症状

- `ros2 topic list` 能看到话题。
- 自己的节点也"订阅"了。
- 但**回调就是不触发**（或时有时无）。

### 1.2 原因

发布方和订阅方的 QoS 兼容性不够。典型组合：

| 发布方 | 订阅方 | 结果 |
| --- | --- | --- |
| BEST_EFFORT | RELIABLE（默认） | 收不到！ |
| RELIABLE | BEST_EFFORT | 能收 |
| 深度 1 | 深度 1 | 能收（但可能丢） |

**为什么默认 RELIABLE 反而收不到 BEST_EFFORT？**
规则：RELIABLE 订阅者要求"保证送达"，但 BEST_EFFORT 发布者不提供 → 不兼容。

### 1.3 排查方法

```bash
ros2 topic info /camera/image_raw/compressed -v
```

输出里看发布者的 `Durability` 和 `Reliability`：

```
Publisher: /xx
  ...
  QoS profile:
    Reliability: BEST_EFFORT
    Durability: VOLATILE
```

**发现发布方是 BEST_EFFORT，而你的订阅方没设置（默认 RELIABLE）→ 就是这个原因。**

### 1.4 解决

```cpp
// 方法 1：用传感器专用 QoS（BEST_EFFORT + 深度 5）
this->create_subscription<T>("/topic",
    rclcpp::SensorDataQoS(), callback);

// 方法 2：显式指定
rclcpp::QoS qos(rclcpp::KeepLast(1));
qos.best_effort();
this->create_subscription<T>("/topic", qos, callback);
```

### 1.5 防坑清单

| 约定 | 建议 |
| --- | --- |
| 图像/点云等"丢一帧没事"的数据 | 两端都用 `SensorDataQoS()` |
| 控制指令/重要数据 | 两端都用默认 RELIABLE |
| 拿不准 | 先 `ros2 topic info -v` 看对方，再照着配 |

## 2. 多线程执行器与线程安全

### 2.1 什么时候需要多线程

默认 `rclcpp::spin` 是**单线程**：所有回调排队执行。
如果你的图像回调要 50ms，那么**定时器和别的回调都会被堵 50ms**。

**需要多线程的典型场景：**

- 一个慢回调（图像处理）+ 一个必须准时的回调（高频控制）。
- 多个互不相干的订阅，想并行处理。

### 2.2 怎么开多线程

```cpp
#include <rclcpp/executors/multi_threaded_executor.hpp>

rclcpp::executors::MultiThreadedExecutor executor(rclcpp::ExecutorOptions(),
                                                   4);   // 4 个线程
executor.add_node(node);
executor.spin();
```

**注意：** 默认 `spin()` 用单线程；`MultiThreadedExecutor` 才会并行。

### 2.3 多线程的代价：数据竞争

两个回调可能**同时**访问同一个变量：

```cpp
// 危险：两个线程同时改 shared_value
void cbA() { shared_value++; }      // 非原子！
void cbB() { shared_value++; }
```

**解决：互斥锁**

```cpp
#include <mutex>

std::mutex mtx_;
double shared_value_ = 0;

void cbA() {
    std::lock_guard<std::mutex> lock(mtx_);   // 自动加锁/解锁
    shared_value_++;
}

void cbB() {
    std::lock_guard<std::mutex> lock(mtx_);
    shared_value_++;
}
```

| 工具 | 什么时候用 |
| --- | --- |
| `std::mutex` + `lock_guard` | 保护复杂共享数据 |
| `std::atomic<int>` | 简单计数/标志位 |
| 只读共享（初始化后不改） | 不用锁 |

### 2.4 更稳的替代方案（推荐给新手）

**把"慢活"移到单独线程，ROS 回调只负责快速搬运数据：**

```cpp
// 回调：只存数据（快）
void imageCallback(const Image::SharedPtr msg) {
    std::lock_guard<std::mutex> lock(mtx_);
    latest_frame_ = cv::imdecode(msg->data, cv::IMREAD_COLOR);   // 尽量快
}

// 单独线程：慢慢处理
std::thread worker([this]() {
    while (rclcpp::ok()) {
        cv::Mat frame;
        {
            std::lock_guard<std::mutex> lock(mtx_);
            if (latest_frame_.empty()) { std::this_thread::sleep_for(10ms); continue; }
            frame = latest_frame_.clone();
        }
        process(frame);        // 慢活在这里，不堵回调
    }
});
```

**好处：** 通信不被计算堵住，数据竞争范围清晰（就一个"最新帧"）。

## 3. 用 bag 离线调试（强烈推荐）

### 3.1 为什么用 bag

- 现场数据稍纵即逝，**录下来就能反复调试**。
- 改一次代码，重放一次，对比结果。
- 不用每次都开游戏/硬件。

### 3.2 工作流

```bash
# ① 录制（现场）
ros2 bag record /camera/image_raw/compressed /autoaim/frame -o test_01

# ② 查看
ros2 bag info test_01

# ③ 重放（调试时）
ros2 bag play test_01

# ④ 另一个终端跑你的节点，观察结果
ros2 run campus_vision campus_node
```

**重放选项：**

```bash
ros2 bag play test_01 -r 0.5       # 慢放 0.5 倍（仔细看）
ros2 bag play test_01 -l           # 循环播放
ros2 bag play test_01 --topics /camera/image_raw/compressed   # 只放某些话题
```

### 3.3 调试技巧

| 技巧 | 做法 |
| --- | --- |
| 固定输入对比输出 | 同一 bag，改代码前后各跑一次 |
| 慢放观察 | `-r 0.5` 甚至 `-r 0.1` |
| 只放必要话题 | 避免无关数据干扰 |
| 存"关键片段" | 小 bag 更容易反复测 |

**注意：** 图像 bag 很大（几分钟就好几 GB），注意磁盘空间，录完及时处理。

## 4. 时间戳：别用错时钟

### 4.1 三种时间

| 时间 | 来源 | 用途 |
| --- | --- | --- |
| 墙上时间 | 系统时钟 | 给人看的、记录时间 |
| 稳定时间 | `steady_clock` | **测耗时**（不受调表影响） |
| ROS 时间 | `node->now()` | **消息时间戳、业务逻辑**（支持仿真） |

### 4.2 测耗时用 steady_clock

```cpp
auto t1 = std::chrono::steady_clock::now();
// ... 要测的代码 ...
auto ms = std::chrono::duration_cast<std::chrono::milliseconds>(
    std::chrono::steady_clock::now() - t1).count();
```

### 4.3 消息时间戳用 node->now()

```cpp
msg.header.stamp = this->now();
```

**为什么？** ROS 2 支持"仿真时间"（`use_sim_time`），
所有节点用统一的 ROS 时钟才能对齐。**涉及消息时间戳的都用 `this->now()`。**

### 4.4 判断数据新旧

```cpp
// 数据是不是太旧了？（延迟超过 250ms 就丢弃）
auto now = this->now();
auto stamp = msg->header.stamp;
auto age_ms = (now - stamp).seconds() * 1000.0;
if (age_ms > 250) {
    // 过期数据，丢弃
    return;
}
```

**这正是校园赛 relay 做的事情：拒收过期帧。**
跨机器（游戏和算法在不同电脑）时，还要先**同步系统时间**（NTP）。

## 5. 性能测量：回调到底多慢

### 5.1 测量回调耗时

```cpp
void processFrame(cv::Mat& frame)
{
    auto t1 = std::chrono::steady_clock::now();
    // ... 处理 ...
    auto ms = std::chrono::duration_cast<std::chrono::milliseconds>(
        std::chrono::steady_clock::now() - t1).count();

    static int n = 0;
    if (++n % 30 == 0) {
        RCLCPP_INFO(this->get_logger(), "processFrame 耗时 %ld ms", ms);
    }
}
```

### 5.2 对比输入输出频率

```bash
ros2 topic hz /camera/image_raw/compressed   # 输入：60Hz
ros2 topic hz /target_angles_player_1        # 输出：只有 20Hz？
```

**输出频率远低于输入 → 你的处理慢了/降频了。**
（校园赛项目就是"每 3 帧处理 1 帧"，60Hz 进 → 20Hz 出，是预期行为。）

### 5.3 定位慢在哪一步

```cpp
double t_total = 0, t_decode = 0, t_contour = 0, t_pnp = 0;
// 每步计时累加，隔一段时间打印各步占比
```

**心法：先测量，再优化。猜"哪里慢"十有八九猜错。**

## 6. 一个更稳的节点架构

综合前面的内容，一个"生产级"的视觉节点长这样：

```
┌─────────────────────────────────────────┐
│ 回调层（快，不阻塞）                      │
│  imageCallback：解码 → 存 latest_frame_  │
│  frameCallback：存 camera_info / state   │
├─────────────────────────────────────────┤
│ 处理层（慢，独立线程）                    │
│  worker 线程：取 latest_frame_           │
│    → 识别 → PnP → 滤波 → 组装 SendData   │
├─────────────────────────────────────────┤
│ 输出层                                   │
│  发布者 + 限频日志 + 状态标记             │
└─────────────────────────────────────────┘
```

要点回顾：

| 要点 | 用到的技术 |
| --- | --- |
| 回调不阻塞 | 快回调 + 独立处理线程 |
| 线程安全 | `std::mutex` + `lock_guard` |
| 数据新鲜度 | 时间戳 + 过期丢弃 |
| 结果稳定 | EMA / 中值滤波 |
| 可复现调试 | bag 录制重放 |
| 性能可见 | 计时打印 + `topic hz` 对比 |
