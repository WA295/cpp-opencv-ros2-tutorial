## 1. 先建立三个认知

### 认知一：程序 = 给计算机的一张"步骤清单"

你写代码，本质上是在写一张**非常精确的菜谱**：

```
1. 打开冰箱
2. 拿出鸡蛋
3. 如果鸡蛋是坏的 → 扔掉，回到第 2 步
4. 打蛋
...
```

计算机只会**严格按你写的步骤执行**，一步不多、一步不少。
它不会"猜"你想干什么。所以：

- 你写"每 3 帧处理 1 帧"，它就真的每 3 帧处理 1 帧；
- 你忘了写"图像为空时跳过"，它就真的会拿着空图像去算，然后崩溃。

**心法：程序的行为不对，先怀疑自己的步骤清单，而不是怀疑计算机。**

### 认知二：写代码 ≠ 运行代码

C++ 是**编译型语言**，流程是：

```
你写的源码（.cpp / .hpp）
      │  编译（编译器：g++ / clang）
      ▼
机器能懂的二进制程序（可执行文件）
      │  运行
      ▼
看到结果 / 报错
```

所以 C++ 的"报错"分两大类：

| 阶段 | 现象 | 典型错误 |
| --- | --- | --- |
| **编译时** | 程序根本没生成 | 语法错、拼写错、找不到头文件、类型不匹配 |
| **运行时** | 程序生成了，跑着跑着挂了 | 段错误（访问了不该访问的内存）、逻辑不对、没反应 |

**心法：先分清是"编译不过"还是"跑不对"，这两类的排查方法完全不同。**

### 认知三：出错是常态，调试才是核心技能

新手最大的误解是"高手写代码不出错"。真相是：

> 高手不是不出错，而是**出错后知道怎么快速定位和解决**。

一份代码从写下到正确运行，90% 的时间花在"找问题"上。
本篇第 4 节会给你一套**调试通用流程**，这是比任何语法都重要的东西。

## 2. 一个 C++ 程序长什么样

### 2.1 最小例子：hello.cpp

```cpp
// hello.cpp —— 第一个程序
#include <iostream>        // 引入"输入输出流"头文件，才能用 cout

int main()                 // main 是程序的入口，必须有且只有一个
{
    std::cout << "你好，世界！" << std::endl;   // 打印一行字
    return 0;              // 返回 0 表示"正常结束"
}
```

逐行解释：

| 代码 | 含义 |
| --- | --- |
| `#include <iostream>` | 把标准库里的"输入输出"功能引进来（相当于 Import） |
| `int main()` | 程序的**入口函数**，操作系统从这里开始执行 |
| `{ ... }` | 花括号包起来的是"代码块" |
| `std::cout << ...` | 输出到屏幕；`std::` 表示"标准库命名空间" |
| `return 0;` | 告诉系统"程序正常结束"（非 0 一般表示出错） |

### 2.2 编译并运行

在终端里：

```bash
g++ hello.cpp -o hello      # 把 hello.cpp 编译成名叫 hello 的可执行文件
./hello                     # 运行它
```

输出：

```
你好，世界！
```

### 2.3 三个必须搞懂的名词

| 名词 | 大白话 | 例子 |
| --- | --- | --- |
| 头文件（.h/.hpp） | 一份"工具清单"，声明有哪些函数/类型可用 | `<iostream>`、`<vector>`、`<opencv2/opencv.hpp>` |
| 源文件（.cpp） | 你写具体逻辑的地方 | `hello.cpp`、`main.cpp` |
| 函数（function） | 一段"打包好的步骤"，起个名字，随时调用 | `main()`、`cv::imread()`、`rclcpp::init()` |

> **为什么要有头文件？**
> 因为一个项目可能有几十个源文件，A 文件想用 B 文件里的函数，就得先"声明"一下。
> 头文件就是这些"声明"的集合：**告诉编译器"有这个东西，长这样"，具体实现写在别处。**

### 2.4 头文件的两种写法

```cpp
#include <vector>       // 尖括号：先找系统/库目录里的头文件（标准库、第三方库）
#include "my_tool.hpp"  // 双引号：先找当前项目目录里的头文件（自己写的）
```

**心法：标准库和库用 `< >`，自己项目里的用 `" "`。**

## 3. 一个项目是怎么做出来的

### 3.1 通用流程（记住这 7 步）

```
① 搞清楚目标：输入是什么？输出是什么？
        ↓
② 拆步骤：把大目标拆成能单独做的小步骤
        ↓
③ 跑通最小版本：先让最简单的功能跑起来（哪怕硬编码）
        ↓
④ 逐步加功能：每次只加一点，加完立刻测
        ↓
⑤ 调试：出问题就用第 4 节的方法定位
        ↓
⑥ 优化：能用了再谈快不快、准不准
        ↓
⑦ 整理：命名、注释、拆分文件，方便以后改
```

### 3.2 用"校园赛视觉节点"演示这个流程

假设要做的事是：**让程序看游戏画面，算出敌人角度，告诉游戏。**

**① 搞清楚输入输出**

| 项目 | 内容 |
| --- | --- |
| 输入 | 游戏画面（JPEG 图片）+ 相机参数 + 自身姿态 |
| 输出 | yaw / pitch 角度 + 开不开火 |

**② 拆步骤**

```
收图 → 找红色灯条 → 把灯条配成装甲板 → 认出装甲板上的数字 → 算它离多远、偏多少 → 发布角度
```

**③ 跑通最小版本**

先别想识别，先做到：**能收到一张图，并把它显示出来**。
这一步跑通，说明"通信 + 解码 + 显示"这条链路是好的。

```cpp
void imageCallback(const sensor_msgs::msg::CompressedImage::SharedPtr msg)
{
    cv::Mat img = cv::imdecode(msg->data, cv::IMREAD_COLOR);
    cv::imshow("test", img);
    cv::waitKey(1);
}
```

**④ 逐步加功能**

1. 加上"每 3 帧处理 1 帧"（省 CPU）
2. 加上颜色分离，把红色区域变亮
3. 加上二值化 + 找轮廓
4. 加上筛选灯条的条件
5. 加上配对
6. 加上 PnP 解算
7. 加上发布

**每加一步就运行一次，确认没坏，再加下一步。**
最忌讳的是：一口气写 500 行，然后发现跑不起来，完全不知道哪一步错了。

**⑤⑥⑦** 见后文。

### 3.3 一个实用的心态

> **能跑 > 好看 > 快**。

新手常见毛病：一开始就追求"架构优雅、算法高级"，结果三天跑不起来，信心崩了。
正确做法是先用最笨的方法跑通（哪怕暴力遍历、哪怕硬编码），再逐步改进。

## 4. 遇到问题怎么办（最重要）

### 4.1 第一步：先看报错信息

编译器报错看着吓人，但它通常已经**告诉你三件事**：

```
main.cpp:25:10: error: 'cameraMatrix' was not declared in this scope
   ^~~~~~~~~~~~
```

| 部分 | 含义 |
| --- | --- |
| `main.cpp:25:10` | **文件:行号:列号** —— 99% 的问题就在这一行或附近 |
| `error:` | 错误级别（error 必须解决；warning 可以暂时忽略） |
| `'cameraMatrix' was not declared in this scope` | 意思："这个作用域里没有叫 cameraMatrix 的东西" |

**新手要养成的第一个习惯：报错第一行 + 行号，永远是第一线索。**

### 4.2 判断问题属于哪一类

| 类别 | 现象 | 先去哪查 |
| --- | --- | --- |
| 编译错误 | 根本没生成程序 | 报错的行号；拼写、分号、头文件、类型 |
| 链接错误 | 提示 `undefined reference` | 库没链上；CMakeLists 少了 `target_link_libraries` |
| 运行时崩溃 | 程序突然退出、`Segmentation fault` | 空指针、数组越界、空 Mat、找不到文件 |
| 逻辑错误 | 能跑，但结果不对 | 打印中间值，逐步缩小范围 |
| 没反应 | 程序不崩也不输出 | 卡在等待、回调没触发、窗口没刷新 |

### 4.3 调试五板斧（把这一节背下来）

#### 板斧 1：打印调试（最常用、最有效）

在你怀疑的地方插入打印，看程序到底走到哪、值是多少：

```cpp
std::cout << "=== 到达第 3 步, area=" << area << std::endl;   // 普通 C++
RCLCPP_INFO(this->get_logger(), "收到 %d 帧", count);            // ROS 2 里
printf("tx=%.3f ty=%.3f tz=%.3f\n", tx, ty, tz);                 // C 风格，简单直接
```

**要点：**

- 打印要带**编号/位置**，比如 `"到A"、"到B"`，看卡在哪一步。
- 打印关键变量，看值是不是你想的（比如 `cameraMatrix_.empty()`）。
- 问题解决后**记得删掉或注释掉**太多打印，否则会刷屏、拖慢程序。

#### 板斧 2：缩小范围（注释法 / 二分法）

如果一大段代码有问题：

1. 把后半段全部注释掉（在代码前加 `//` 或 `/* ... */`），看前半段是否正常。
2. 正常 → 问题在后半段；不正常 → 问题在前半段。
3. 对"有问题的那一半"再切一半……重复几次就能锁定到几行。

#### 板斧 3：做"最小可复现例子"

当你的代码很复杂、错误说不清时：

- 新建一个干净的小文件，**只保留能复现问题的最少代码**。
- 往往在"删代码"的过程中，你自己就发现问题了。

> 这也是提问的正确姿势：别人不喜欢看 500 行代码，但很喜欢看 20 行能复现问题的例子。

#### 板斧 4：善用搜索

搜索时**关键词怎么选**很关键：

| 差的搜法 | 好的搜法 |
| --- | --- |
| "程序为什么报错" | `c++ "was not declared in this scope"` |
| "opencv 显示不了" | `opencv imshow 窗口不刷新 waitKey` |
| "ros2 收不到消息" | `ros2 topic echo 没有数据 ROS_DOMAIN_ID` |

**技巧：把编译器报错原文（英文）整段粘进去搜，效果最好。**

#### 板斧 5：断点调试（进阶）

用 VSCode 或 gdb 可以在某一行"暂停"程序，然后看所有变量的值：

```bash
g++ -g main.cpp -o main    # -g 表示"带上调试信息"
gdb ./main                 # 启动调试器
(gdb) break main.cpp:25    # 在第 25 行下断点
(gdb) run                  # 运行，会在断点处停下
(gdb) print area           # 查看变量 area 的值
(gdb) next                 # 执行下一行
(gdb) continue             # 继续运行
```

> 先用好板斧 1 和 2，等熟练了再上断点调试。

### 4.4 调试流程图（贴在脑子里）

```
出问题了
   │
   ├─ 编译不过？ → 看第一行报错 + 行号 → 拼写/头文件/类型
   │
   ├─ 跑着崩了？ → 空指针？越界？文件没打开？ → 在崩溃前打印
   │
   ├─ 能跑但不对？ → 打印中间值 → 缩小范围 → 二分法
   │
   └─ 没反应？ → 程序是否卡住/在等？回调是否触发？打印"进入函数"
```

### 4.5 提问的正确姿势

如果自己搞不定，要问人/发帖，请提供：

1. **你想做什么**（目标）
2. **你写了什么**（关键代码，不要全贴）
3. **报错/现象原文**（完整复制，别转述）
4. **你已经试过什么**（证明你努力过）
5. **环境**：系统、编译器版本、库版本（如 Ubuntu 24.04 + OpenCV 4.6 + ROS 2 Jazzy）

## 5. 代码怎么组织才不乱

### 5.1 命名

| 类型 | 习惯写法 | 例子 |
| --- | --- | --- |
| 变量 | 小写 + 下划线 | `frame_count`、`image_sub_` |
| 函数 | 动词开头，小写+下划线 | `processFrame`、`pointdistance` |
| 类型/类 | 大驼峰 | `CampusNode`、`Armor` |
| 常量 | 全大写 | `ARMOR_WIDTH_M` |

> 命名最重要的原则是：**看名字就知道是干嘛的**。`a1`、`tmp`、`data2` 这类名字要尽量避免。

### 5.2 注释

- 文件顶部：说明这个文件干嘛的、作者、日期。
- 函数上方：说明参数、返回值、注意事项。
- 关键逻辑旁：说明"为什么这么做"（而不是复述代码）。

```cpp
// 好注释：解释为什么
// 红色通道减蓝色通道，因为灯条是红色的，减去蓝色能让背景变暗
cv::subtract(channels[2], channels[0], red_diff);

// 坏注释：复述代码（没意义）
// 这是 subtract 函数
cv::subtract(channels[2], channels[0], red_diff);
```

### 5.3 函数拆分

一个函数别写太长。经验值：

- **一个函数只做一件事**。
- 超过 100 行就该考虑拆。
- 拆出来的函数如果只在类内部用，就写成成员函数；如果是通用小工具，就写成自由函数。

### 5.4 全局变量 vs 成员变量 vs 局部变量

| 类型 | 放哪 | 什么时候用 |
| --- | --- | --- |
| 局部变量 | 函数内部 | 只在函数里用一次的数据（绝大多数情况） |
| 成员变量 | 类里，带下划线 | 多个函数都要访问、需要在回调间传递的数据（如相机参数） |
| 全局变量 | 文件最上方 | 尽量少用；调参常量可以（如阈值） |

> 校园赛项目里：`cameraMatrix_`、`last_state_` 是成员变量（两个回调共享），
> `thresholdValue` 是全局变量（可调参数），`red_diff` 是局部变量。

## 6. 学习路线与常见误区

### 6.1 建议路线

```
第 1 步：会写 hello world，会用 g++ 编译
   ↓
第 2 步：掌握 C++ 基础（变量/循环/函数/数组/结构体）      → 01-C++/00
   ↓
第 3 步：会用标准库常用函数（sort/string/vector...）       → 01-C++/01
   ↓
第 4 步：会加图片显示、颜色转换、找轮廓                     → 02-OpenCV/00~02
   ↓
第 5 步：理解相机、PnP、测距                                → 02-OpenCV/03
   ↓
第 6 步：理解节点/话题/消息，能收发消息                     → 03-ROS2/00~01
   ↓
第 7 步：能独立写一个"订阅→处理→发布"的节点                → 03-ROS2/04
   ↓
第 8 步：能读懂并修改一个真实项目                          → 04-综合实战
```

### 6.2 常见误区

| 误区 | 正解 |
| --- | --- |
| 先把语法书背完再动手 | **边做边学**最快；先跑通小例子，遇到不会的再查 |
| 一上来就写好几百行 | 小步快跑，每加一点就测试 |
| 报错就慌、不看报错 | 报错是朋友，第一行 + 行号永远是钥匙 |
| 复制代码不改就交 | 你要知道每行干嘛；不懂就查/打印验证 |
| 追求"高级写法" | 能跑、能懂、能改 > 花哨 |
| 不敢删代码试 | 有 git 就能放心试；测试是最好的老师 |

### 6.3 一句话总结

> **想清楚输入输出 → 拆小步骤 → 先跑通 → 逐步加 → 出错就打印和缩小范围。**

把这句话记牢，再配合后面三大部分的函数手册，你就能从"小白"走到"能自己写项目"。
